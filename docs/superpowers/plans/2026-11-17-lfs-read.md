# Git LFS in read, for team containers — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A role with `"lfs": true` gets the LFS content of its repository in `/workspace`: the host fetches the LFS objects into the team's origin mirror with the forwarded SSH agent, and the container reads them from that read-only mirror, with no network and no credential.

**Architecture:** Three small changes on the existing paths, no new command. (1) `lfs` is a role field, carried by `Member`. (2) `mirror.ts` gets `fetchMirrorLfs`, called where the mirror is created (`provisionMember`) and refreshed (`forge team sync`), for a team when any of its `repo` roles asks for LFS. (3) `cloneWorkspace` and `pointOriginAtMirror` take the LFS mode: the clone smudges from the mirror through git-lfs's standalone file transfer, and `lfs.url` and `lfs.standalonetransferagent` are written to the workspace's `.git/config`, which beats any `.lfsconfig` the repository carries.

**Tech Stack:** TypeScript on Node 24 (`node --test`), git-lfs 3.7 on the host (Ansible installs it) and in the image (already there), Incus disk devices.

**Spec:** `docs/superpowers/specs/2026-10-20-dx-chapter-design.md`, « Git LFS, optional » (the read half; its « first `forge start` » activation is replaced by the role's `lfs`, see the maintainer's comment on #89). Spike: `docs/superpowers/spikes/2026-11-17-lfs-lecture.md`. Out of scope: writing LFS objects (#168).

## Global Constraints

- Branch `agent/lfs-lecture`, from `origin/main`; one pull request, `Refs #89`. Title: `feat: Git LFS en lecture dans les containers d'une équipe`.
- The role key is `lfs`, a boolean, default `false`, valid only on a role that has the `repo` capability (the config parser refuses it elsewhere, naming the key). The origin mirror belongs to the team: its LFS objects are fetched when at least one `repo` role of the team has `lfs: true`; a container reads them only if its own role has it.
- Host side, every fetch gets what it trusts on the command line: the repository URL (as `refreshMirror` does), `lfs.url` set to that same URL, and the SSH-only protocol options of `GITHUB`. A `.lfsconfig` of the repository must never choose where the host sends its credentials: in a bare repository git-lfs reads `HEAD:.lfsconfig`.
- Which refs: the default branch of the mirror (`HEAD`), nothing else, never `--all` (a LFS file has one version per commit that changes it: spike, « Ce qu'il faut retenir » 3). The agent branches live in the team mirror and belong to the write half.
- Container side, a role with `lfs: true` has the LFS filters installed **without** `--skip-smudge`, before the clone: the current `LFS_FILTERS_INSTALL` writes `smudge --skip` in the user's `~/.gitconfig`, which wins over `/etc/gitconfig` and would leave pointers even with the mirror configured. A role without `lfs` is unchanged: `GIT_LFS_SKIP_SMUDGE=1`, skip-smudge filters.
- No new network path: the container reads files of the mirror, so strict mode needs no allowlist entry, and no credential enters the container.
- `git-lfs` is a package of the host (`base_packages`), never installed by `forge`; `forge team converge` refuses a team with an `lfs` role on a host that lacks it, naming the package.
- Lean tests: the argv shapes (each checked against what its consumer reads), the config validation, the capability rule, one contract test with a real git-lfs. Nothing tests documentation.
- Docs and plan in English; `container/CLAUDE.md` in French. Commits: conventional prefix, French message.

## Review Focus

1. **A repository choosing where the host fetches.** A `.lfsconfig` in the mirror's `HEAD` pointing `lfs.url` elsewhere must not change the host's fetch (Task 3, with the real git-lfs on the test VM).
2. **Pointers that stay pointers.** A container provisioned with `lfs: true` whose `~/.gitconfig` still holds `smudge --skip` reads nothing; the contract test of Task 5 reproduces the container's two-level config.
3. **A reused workspace.** A workspace created before `lfs` was turned on keeps pointers until `git lfs pull`; the realign step must write the config and say so (Task 5).
4. **The host without git-lfs.** `converge` refuses before creating anything (Task 2).

### Task 3: Fetch the LFS objects into the mirror

**Files:**
- Modify: `cli/lib/mirror.ts` (`fetchMirrorLfs`)
- Modify: `tests/mirror.test.ts`

`fetchMirrorLfs(ctx, mirror, ownerRepo, remote = GITHUB)` runs:

```
git --git-dir=<mirror> <remote.protocol> -c lfs.url=<remote.url(ownerRepo)> lfs fetch <remote.url(ownerRepo)> HEAD
```

with `GIT_OPTS`, validating `ownerRepo` like `refreshMirror`, and returns the `ExecResult` for the caller to judge.

- [ ] **Step 1: Check the two assumptions on the test VM before writing code** (the spike used HTTPS and a repository without `.lfsconfig`). With the real git-lfs in a bare clone: (a) `git lfs fetch <url> HEAD` accepts a URL where it expects a remote name; if not, fall back to `-c remote.origin.url=<url>` plus `lfs fetch origin HEAD`, and say so in the code's comment; (b) with `-c lfs.url=…` a `HEAD:.lfsconfig` that names another `lfs.url` changes nothing (a local commit in a bare repository is enough, as in the spike's `hostile` branch). If (b) fails, the plan stops here and the maintainer decides: the host would then have to read the LFS pointer list itself.
- [ ] **Step 2:** Failing test on the argv with a fake `exec`: `--git-dir`, the protocol options before `lfs`, `-c lfs.url=` equal to the command-line URL (not read from the mirror's config), the ref `HEAD`, no `--all`; an invalid `ownerRepo` rejects.
- [ ] **Step 3:** Implement. Commit `feat: fetchMirrorLfs récupère les objets LFS dans le miroir, l'URL en ligne de commande (#89)`.

### Task 5: The container reads from the mirror

**Files:**
- Modify: `cli/lib/mirror.ts` (`LFS_MIRROR_CONFIG`; `cloneWorkspace(ctx, container, lfs)`; `pointOriginAtMirror(ctx, container, lfs)`)
- Modify: `cli/lib/commands/provision.ts` (`LFS_FILTERS_READ = "git lfs install --skip-repo"`, `LFS_HOOKS_READ = "git lfs install"`)
- Modify: `cli/lib/team-provision.ts` (order and flags, below)
- Modify: `tests/mirror.test.ts` (the `GIT_LFS_SKIP_SMUDGE=1` case stays for `lfs = false`), `tests/contract/lfs.test.ts`

For `lfs = true`:

- the filters are installed **before** the clone, with `LFS_FILTERS_READ`, so that no `smudge --skip` reaches `~/.gitconfig`;
- the clone is `git -c lfs.url=file:///forge/origin.git -c lfs.standalonetransferagent=lfs-standalone-file clone --no-local /forge/origin.git /workspace`, without `GIT_LFS_SKIP_SMUDGE`;
- right after it, both keys go into `/workspace/.git/config` (`git config`), so a later checkout, rebase or `git lfs pull` reads the mirror and not a `.lfsconfig`. `pointOriginAtMirror` writes the same two keys for a reused workspace, and `provisionMember` prints, for that case, that a workspace created before `lfs` is turned on keeps pointers until `git lfs pull`;
- the later `LFS_FILTERS_INSTALL` step is replaced by `LFS_FILTERS_READ`, and the hooks step by `LFS_HOOKS_READ`.

- [ ] **Step 1:** Failing unit tests on the argvs (`lfs` true and false; the `-c` options sit before `clone`; the two `git config` calls; no `GIT_LFS_SKIP_SMUDGE` when true).
- [ ] **Step 2:** Failing contract test (real git-lfs, temporary `HOME`, as the existing file does): a mirror holding one LFS object, a global config made by `LFS_FILTERS_READ`, the clone above gives the content, and then a checkout of a branch whose `.lfsconfig` names another `lfs.url` still gives the content. A second case with the old `LFS_FILTERS_INSTALL` documents why the read mode needs its own install (pointers). Skipped without git-lfs, except under CI, like the file's other cases.
- [ ] **Step 3:** Implement; `provisionMember` passes `m.lfs`.
- [ ] **Step 4:** `npm test`, commit `feat: un container lfs lit le contenu LFS dans le miroir, sans réseau (#89)`.
